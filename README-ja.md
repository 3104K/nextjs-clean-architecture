## クリーンアーキテクチャ

![Clean Architecture Diagram](./assets/clean-architecture-diagram.jpg)

クリーンアーキテクチャについて初めて聞く方には、[Uncle Bob によるオリジナルの記事](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)を読むことを強くおすすめします。ここでは私なりに要約してみます。

クリーンアーキテクチャは、アプリケーションを保守しやすく、テストしやすく、コードベースを予測可能な形に構造化するための _ルールの集合_ です。技術的なバックグラウンドや好みのプログラミング言語に関係なく、開発者同士が理解できる共通言語のようなものです。

クリーンアーキテクチャと、それに類似・派生するアーキテクチャは、どれも同じ目標を持っています。それは _関心の分離（separation of concerns）_ です。これらのアーキテクチャは、似たコードをまとめる **レイヤー（層）** を導入します。この「レイヤー化」によって、コードベースにおける次のような重要な性質を実現できます。

- **UI からの独立** - ビジネスロジックは、使用している UI フレームワーク（この場合は Next.js）と結合していません。ビジネスロジックやルールを変更することなく、同じシステムを CLI アプリケーションでも使えます。
- **データベースからの独立** - データベースの実装や操作は独自のレイヤーに分離されています。そのため、アプリケーションの他の部分はどのデータベースを使っているかを気にせず、_モデル（Models）_ を使ってやり取りします。
- **フレームワークからの独立** - ビジネスルールとロジックは、外の世界について一切知りません。プレーンな JavaScript で定義されたデータを受け取り、プレーンな JavaScript、_サービス（Services）_、_リポジトリ（Repositories）_ を使って独自のロジックと機能を定義します。これにより、システムをフレームワークの実装や制約に合わせて「型にはめる」のではなく、フレームワークを道具として使えます。たとえばアプリで Route Handlers を使っていて、その一部を Server Actions にリファクタリングしたい場合でも、Route Handler の代わりに Server Action から特定の _コントローラー（controllers）_ を呼び出すだけで済み、_コア_ となるビジネスロジックは変わりません。
- **テスト可能** - ビジネスロジックとルールは、UI フレームワーク、データベース、Web サーバー、その他システムを構成する外部要素に依存しないため、簡単にテストできます。

クリーンアーキテクチャは、_依存関係の階層_ を定義することでこれを実現します。各レイヤーは **自分より下の** レイヤーにのみ依存し、上のレイヤーには依存しません。

## プロジェクト構成（重要な部分のみ）

- `app` - **Frameworks & Drivers 層** - Next.js に関するもの全般（ページ、Server Actions、コンポーネント、スタイルなど）や、アプリのロジックを「利用する」ものすべて
- `di` - 依存性の注入（Dependency Injection） - DI コンテナとモジュールをセットアップするフォルダ
- `drizzle` - DB に関するものすべて - DB クライアントの初期化、スキーマ定義、マイグレーション
- `src` - システムの「ルート」
  - `application` - **Application 層** - ユースケースと、リポジトリ・サービスのインターフェースを置く
  - `entities` - **Entities 層** - モデルとカスタムエラーを置く
  - `infrastructure` - **Infrastructure 層** - リポジトリとサービスの実装を置く。インターフェースは `application` から取り込む
  - `interface-adapters` - **Interface Adapters 層** - システムへのエントリーポイントとなるコントローラーを置く（Frameworks & Drivers 層からシステムとやり取りするために使う）
- `tests` - ユニットテストを置く場所 - `unit` サブフォルダの構成は `src` と対応している
- `.eslintrc.json` - `eslint-plugin-boundaries` プラグインを定義している場所 - _これにより依存関係のルールを破れないようにしている_
- `vitest.config.ts` - `@` エイリアスの定義方法に注目してください！

## 各レイヤーの説明

- **Frameworks & Drivers**: UI フレームワークのすべての機能と、システムとやり取りするその他すべてのもの（例: AWS Lambda、Stripe の Webhook など）を保持します。このプロジェクトでは、Next.js の Route Handlers、Server Actions、コンポーネント（Server と Client）、ページ、デザインシステムなどがこれにあたります。
  - このレイヤーは _コントローラー_、_モデル_、_エラー_ のみを使うべきで、_ユースケース_、_リポジトリ_、_サービス_ を使っては **いけません**。
- **Interface Adapters**: _コントローラー（Controllers）_ を定義します。
  - コントローラーは、入力を特定のユースケースに渡す前に **認証チェック** と **入力バリデーション** を行います。
  - コントローラーはユースケースを _オーケストレーション_ します。自身ではロジックを実装せず、ユースケースを使って操作全体を定義します。
  - より深いレイヤーで発生したエラーは上位へ伝播し、コントローラーを使っている場所で処理されます。
  - コントローラーは、データを「利用者」に返す直前に _プレゼンター（Presenters）_ を使って UI で扱いやすい形式に変換します。これにより、クライアントに送る JavaScript（データ変換のためのロジックやライブラリ）を減らせます。また、メールアドレスやハッシュ化されたパスワードのような機密性の高いプロパティの漏洩を防ぎ、クライアントに返すデータ量を減らすことにも役立ちます。
- **Application**: ビジネスロジックが置かれる場所です。_コア_ と呼ばれることもあります。このレイヤーでは、ユースケースと、サービスおよびリポジトリのインターフェースを定義します。
  - **ユースケース（Use Cases）**:
    - 「Todo を作成する」「サインインする」「Todo の完了状態を切り替える」のような、個々の操作を表します。
    - （コントローラーで）バリデーション済みの入力を受け取り、_認可チェックを行います_。
    - _リポジトリ_ と _サービス_ を使って、データソースにアクセスしたり外部システムと通信したりします。
    - **ユースケースは他のユースケースを使うべきではありません**。それはコードの不吉な臭い（code smell）です。そのユースケースが複数のことを行っているという意味であり、複数のユースケースに分割すべきです。
  - リポジトリとサービスのインターフェース:
    - これらをこのレイヤーで定義するのは、それらが使うツールやフレームワーク（データベースドライバー、メールサービスなど）への依存を切り離したいからです。実装は _Infrastructure_ 層で行います。
    - インターフェースがこのレイヤーにあるため、ユースケース（および推移的に上位のレイヤー）は _依存性の注入（Dependency Injection）_ を通じてそれらにアクセスできます。
    - _依存性の注入_ によって、**定義**（インターフェース）と **実装**（クラス）を分離し、実装を別のレイヤー（infrastructure）に置いたまま利用できるようになります。
- **Entities**: _モデル（Models）_ と _エラー（Errors）_ を定義する場所です。
  - **モデル**:
    - 「データベース」の技術を使わず、プレーンな JavaScript で「ドメイン」のデータの形を定義します。
    - モデルは必ずしもデータベースと結びついているわけではありません。たとえばメール送信にはデータベースではなく外部のメールサービスが必要ですが、それでも「メールを送信する」ことを他のレイヤーとやり取りするためのデータの形は必要です。
    - モデルは独自のバリデーションルールも定義します。これは「エンタープライズビジネスルール（Enterprise Business Rules）」と呼ばれます。通常は変わらないルール、あるいは _外部_ の何か（ページ遷移、セキュリティなど）が変わったときにも最も変わりにくいルールです。例としては、ユーザー名フィールドを _6 文字以上で、特殊文字を含まない_ ものと定義する `User` モデルが挙げられます。
  - **エラー**:
    - 独自のエラーを用意するのは、データベース固有のエラーや、特定のライブラリ・フレームワークに固有のエラーを上位に伝播させたくないからです。
    - 他のライブラリ（たとえば Drizzle）から来るエラーを `catch` し、独自のエラーに変換します。
    - こうすることで、_コア_ をあらゆるフレームワーク、ライブラリ、技術から独立させておけます。これはクリーンアーキテクチャの最も重要な側面のひとつです。
- **Infrastructure**: _リポジトリ_ と _サービス_ を定義する場所です。
  - このレイヤーは、_Application 層_ からリポジトリとサービスのインターフェースを取り込み、それぞれのクラスで実装します。
  - _リポジトリ_ は、データベース操作を実装する手段です。`getTodo`、`createTodo`、`updateTodo` のように、単一のデータベース操作を行うメソッドを公開するクラスです。つまり、データベースのライブラリやドライバーはこれらのクラスの中でのみ使います。リポジトリはデータのバリデーションを行わず、データベースに対してクエリやミューテーションを実行し、独自に定義した _エラー_ を投げるか、結果を返すだけです。
  - _サービス_ は、アプリケーション全体で使われる共通のサービスです。認証サービスやメールサービスのほか、Stripe のような外部システム（決済の作成、レシートの検証など）を実装するものもあります。これらのサービスも他のフレームワークやライブラリを使い、それらに依存します。そのため、実装はリポジトリと一緒にこのレイヤーに置かれています。
  - どのレイヤーもこのレイヤーに依存させたくない（そして推移的にデータベースや全サービスに依存させたくない）ので、[_依存性逆転の原則（Dependency Inversion principle）_](https://en.wikipedia.org/wiki/Dependency_inversion_principle)を使います。これにより、_Infrastructure 層_ の実装ではなく、_Application 層_ で定義されたインターフェースだけに依存できます。[ioctopus](https://github.com/Evyweb/ioctopus) のような [_制御の反転（Inversion of Control）_](https://en.wikipedia.org/wiki/Inversion_of_control) ライブラリを使って、実装をインターフェースの背後に抽象化し、必要なときに「注入」します。この抽象化は `di` ディレクトリで作成します。リポジトリ、サービス、コントローラー、ユースケースを Symbol に「バインド」し、実際の実装が必要なときにその Symbol を使って「解決（resolve）」します。こうすることで、実装に明示的に依存する（import する）ことなく、実装を利用できます。

<details>
  <summary><b>クリーンアーキテクチャ／この実装はサーバーレスに対応していますか？Vercel にデプロイできますか？</b></summary>

はい！Page Router、App Router、Middleware、API Handlers、Server Actions など、何とでも組み合わせて使えます。JavaScript プロジェクトで依存性の注入を実現する場合、通常は [Inversify.js](https://inversify.io) ライブラリが使われますが、これは Node 以外のランタイムとは互換性がありません。このプロジェクトでは、`reflect-metadata` に依存せず、すべてのランタイムで動作するシンプルな IoC コンテナである [ioctopus](https://github.com/Evyweb/ioctopus) を採用しています。

</details>

<details>
  <summary><b>Next.js プロジェクトを作成したら、すぐにクリーンアーキテクチャを導入すべきですか？</b></summary>

私の答えは **いいえ** です。まったく新しいプロジェクトを始めるなら、できるだけ早く MVP の段階に到達することに集中するようおすすめします（アイデアを検証したり、プロジェクトに将来性があるかを見極めたりするためです）。物事が本格的になってきたとき（実装する機能が増えてきた、ユーザー数が大きく伸びた、他の開発者をプロジェクトに迎え入れるようになった、など）こそ、このアーキテクチャ（あるいはどんなアーキテクチャでも）の導入に時間を投資すべきタイミングです。

すでにプロジェクトにどっぷり浸かっている場合は、あなた（とチーム）で次のスプリントから段階的なリファクタリングを計画できます。この場合、コードはすでに書かれているので、少し整理し直すだけです。それも、Route Handler ごと、Server Action ごとに、少しずつ進められます。ちなみに _「少し整理し直すだけ」_ と軽く言いましたが、実際にはそこまで単純ではないこともあります。リファクタリングを計画するときは、常に「うまくいかないこと」を考慮に入れてください。そして、テストを書く時間も確保しましょう！

</details>
<details>
<summary><b>これはオーバーエンジニアリングに見えますし、機能開発を複雑にしているのでは？</b></summary>

3 分以上考えないのであれば、確かにオーバーエンジニアリングに見えるでしょう。しかし、よく考えてみれば **アーキテクチャ = 規律** であることに気づくはずです。アーキテクチャは、何をどこに置くかを定めた開発者間の契約です。コードベースを予測可能にし、そうした判断を代わりに下してくれるので、実際には機能開発を **シンプル** にしてくれます。

プロジェクトに関わる開発者全員が、それぞれ一番都合のよい場所にコードを書いていたら、プロジェクトを持続的に成長させることはできません。コードベースは扱うのが悪夢のような状態になり、そのときこそ本当に複雑な機能開発プロセスを実感することになるでしょう。これに対抗するために、いずれはいくつかのルールを定めることになります。そのルールは、チームが新しい問題に直面し、それを解決するたびに増えていきます。それらのルールをすべてドキュメントにまとめれば、それがあなた独自のアーキテクチャ定義です。結局は何らかのアーキテクチャを導入しているのですが、そこに至るまでにとても長く苦しい道のりをたどっただけなのです。

クリーンアーキテクチャは、近道と、実績のある定義済みのアーキテクチャを提供してくれます。もちろん、これらすべてを学ぶ必要はあります。しかし、学ぶのは一生に一度だけで、あとは将来使うどんな言語やフレームワークでもその原則を適用すればよいのです。

</details>
<details>
<summary><b>すべてのプロジェクトにクリーンアーキテクチャを適用すべきですか？</b></summary>

**いいえ**。機能の数、ユーザー数、関わる開発者の数のいずれにおいても、プロジェクトが成長する見込みがないのであれば、適用する必要はありません。

</details>
